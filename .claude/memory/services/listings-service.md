# Listings Service Status

## Location
`backend/apps/listings-service/`

## Implemented Modules
- **projects** — full CRUD, publish flow, media upload, CMS sync. Scoring fields added (rating, reviewCount, completionsCount, views90d, adminBoost, featured)
- **services** — `ServicesModule` registered, full CRUD at `/v1/services`, scoring fields added
- **teams** — `TeamsModule` registered, full CRUD at `/v1/teams`, scoring fields + team-specific (logo, specializations, completedProjects)
- **job-listings** — most complete module with phases, tasks, budget, AI, invites, RabbitMQ events
- **publish** — project publishing pipeline with relational persistence, media entities
- **cms-projects** — raw SQL read adapter at `/v1/projects` for homepage (reads from `projects` table with scoring fields)

## Database Tables
| Table | Status | Notes |
|-------|--------|-------|
| `projects` | Exists | 12 seed rows with Unsplash images + scoring data |
| `services` | Exists | 6 seed rows with Unsplash images + scoring data (auto-created by TypeORM synchronize) |
| `teams` | Exists | 6 seed rows with Unsplash images + scoring data (auto-created by TypeORM synchronize) |
| `project` | Exists | TypeORM entity table (separate from `projects`), has `cmsId` field |
| `job_listings` | Exists | Complex schema with phases, tasks, team members |

## Scoring Fields (added 2026-04-09)
All three listing entities (Project, Service, Team) now have:
- `rating` (numeric 3,1, default 0)
- `reviewCount` (int, default 0)
- `completionsCount` (int, default 0)
- `views90d` (int, default 0)
- `adminBoost` (numeric, default 0)
- `featured` (boolean, default false)

Team entity also has: `logo`, `specializations[]`, `completedProjects`

- **Slug generation (PMCM-254, 2026-10-06)**: `updateProjectDraft` (`publish.service.ts`) and the legacy `projects.service.ts update()` both used to recompute `slug = slugify(title)` on every title edit, with no check against the project's existing slug — any title edit after first save silently changed the published URL. Fixed: both now only set `slug` when the project doesn't already have one (`!existing.slug`). `createProjectDraft`/legacy `create()` are correctly unconditional (first save). No DB path left unaudited — `project-sync.service.ts`'s two slug touches are plain pass-through of a CMS-supplied slug, not generation, and were left alone.
- **DTO validation added (PMCM-254)**: `UpsertProjectDraftDto`/`CreateProjectDto`.title now has `@MaxLength(120)` (entity column already had `length: 120`, DTO didn't enforce it); `.categories`/`.categorySelections` now have `@ArrayMaxSize(3)` — safe, both editors already cap category count to 3 on hydration regardless of what's stored. `ProjectCategorySelectionDto.subCategories` deliberately does **not** have `@ArrayMaxSize(5)` — it was added and then removed in the same ticket once traced: this DTO is nested inside the autosave/upsert payload, and neither editor caps `subCategories` on hydration (both copy an existing listing's subcategories verbatim), so a listing with >5 subcategories in any row (e.g. from the legacy `projects.service.ts` module, which has zero validation) would 400 on every wizard autosave (not validity-gated, resends full form state) and on any inline-editor Categories-tab save. The 5-item cap stays client-side-only (both editors already block a 6th addition with "You can add a maximum of five (5) sub-categories."). Do not re-add the DTO cap without first either verifying staging/live has no over-5 rows, or adding a hydration-time trim — and trimming silently drops a seller's existing data on their next save, so that needs explicit product sign-off too, not a silent slice(0,5).
- **Rich-text description sanitization added (PMCM-255, 2026-10-06)**: `fullDescription` arrives straight from the talent's own browser (Tiptap HTML, via `createProjectDraft`/`updateProjectDraft` in `publish.service.ts`) and was never sanitized server-side. Added module-level `sanitizeProjectFullDescription()` reusing the already-installed `sanitize-html` npm package (same dependency `job-listing.service.ts`'s `sanitiseRichText` already uses, just with a wider allow-list to match what the frozen `RichTextEditor` actually produces: `span[data-font-size]` for heading-size marks, `img[data-align]` for inline images, `blockquote`). Wired into both draft-creation paths. Deliberately does **not** restrict `img src` to a specific origin at this layer — the two upload paths below resolve their CDN origin inconsistently (`CLOUDFLARE_R2_PUBLIC_URL` vs `CLOUDFLARE_PUBLIC_URL`). **Follow-up correction (2026-10-07)**: the frontend sanitizer was originally meant to pick up the origin-restriction instead, but that was reverted — see the next entry. Both layers are scheme-allow-list only (`https`/`http`) now, not origin-restricted; that's an accepted gap, not an oversight.
- **Two parallel, non-presigned image upload paths exist (found during PMCM-255, not consolidated)**: `/publish/media` (gallery images → `publish.service.ts`'s `createProjectOfMedia` → `CloudflareStorageService`, 5MB cap, jpeg/png/webp only, `ImageValidator`) and `/publish/rich-text-image` (description inline images → API gateway's `publish-rich-text-image.controller.ts` → listings-service's separate `v1/media` module/`MediaService`, 10MB cap, any image mimetype, different R2 env var names). Both are backend-mediated multipart uploads — neither actually uses a pre-signed URL, despite that being assumed by PMCM-255's ticket text. Consolidating them is a real gap worth picking up but was judged out of scope for that ticket's pass.
- **`DELETE /v1/media/:key` exists but is dead code (found during PMCM-255)**: `media.controller.ts` defines it, `media.service.ts` implements the R2 `DeleteObjectCommand`, but there is no auth guard on the route and the API gateway does not proxy it (only `POST /publish/rich-text-image` is proxied) — nothing in the frontend calls it either. The frozen `RichTextEditor`'s embedded-image delete flow (confirmed via grep: `tr.delete(pos, ...)`) only removes the ProseMirror node from the editor's own document; it never calls this or any other backend delete. Same for image replace/edit-rotate — the previous storage object is never cleaned up. Before wiring this up: add an auth guard + ownership check to the controller, add a gateway proxy route, and the calling code would need to live inside the frozen `RichTextEditor` component (currently off-limits) since that's where the delete/replace actions are triggered.
- **Frontend image-src allow-list corrected (PMCM-255 follow-up 2, 2026-10-07)**: the original pass's `sanitizeProjectDescription` (`frontend/lib/sanitize-html.ts`) restricted `<img src>` to a `storageOrigin` param backed by a new `getPublicR2CdnBase()`/`NEXT_PUBLIC_R2_CDN_BASE` — but that env var isn't in any committed frontend env template, so on staging/live the origin was always empty and every description image got stripped; the `startsWith` check was also spoofable. Reverted: `getPublicR2CdnBase()` removed from `runtime-urls.ts`, `sanitizeProjectDescription` now takes no origin argument and allow-lists by `URL` parse + `https:`/`http:` scheme only (same scheme-only approach `sanitizeProjectFullDescription` already uses backend-side — see above). Neither layer does origin-restriction now; that's accepted, not a regression to re-flag.
- **Project media upload validator updated (PMCM-256, 2026-10-08)**: `ImageValidator` (`publish.module.ts`) maxSize changed `5MB → 10MB` and `image/webp` dropped from `allowedMimeTypes`; `mediaFileFilter`'s image-field regex (`upload.validator.ts`, the one actually gating `POST /publish/media` via its multer `fileFilter`) also dropped `webp` from its extension match — both scoped to the image fields only, the video-field branch and the dead/unused `imageFileFilter` export were left alone. This only gates NEW uploads: nothing in the read/display path re-validates mimetype, so existing `.webp` URLs already in a project's `featuredImage`/`additionalImages` keep rendering and keep being accepted as "no change" on re-save. Confirmed this is the single source of truth for the 5MB (now 10MB) constant — only one literal, consumed (not redefined) by `ImageValidator` itself, so there was nothing else to change. Also confirmed, report-only: the upload chain (`POST /publish/media`, shared by featured image and gallery) is fully backend-mediated multipart end to end (frontend → api-gateway's `publish-media.controller.ts` rebuilds FormData → listings-service's own multer interceptor → `cloudflareStorageService.uploadProjectMedia`'s `PutObjectCommand`) — no pre-signed URL is generated or returned anywhere in this path, and moderation runs server-side at publish time (`publishExistingProject` → `moderateImageUrl`/`moderateVideoUrl`), not at upload time; `ModerationUnavailableError` (503/`publish_blocked`) and an explicit `rejected` moderation status are already distinguished by the caller.
- **`handleGalleryDelete`'s index-shift bug (found + fixed during PMCM-256)**: the inline editor's `project.mediaUrls` persists through `PUT /publish/media/:projectId/gallery` → `updateMediaGallery` (`publish.service.ts`), confirmed via that method's own code to store whatever `additionalImages` array shape it's handed **verbatim** (`mediaRepository.update(existingMedia.id, { additionalImages, hiddenImages })`, no compaction) — so a frontend gap-stripping bug is a true persistence bug, not just a render glitch. Four frontend call sites were silently compacting the array with `.filter()` before sending it (dropping blank/blob entries instead of keeping them in place), which desynced the persisted order from the grid's fixed-by-index slots on the next load; all four now `.map()` to `""` in place. See `progress.md`'s PMCM-256 entry for the full list of call sites fixed.
- **No team-member capacity data exists anywhere (confirmed during PMCM-257, read-only — nothing changed)**: `backend/apps/user-service`'s `talent-profile.entity.ts`/`user.entity.ts` both have only a generic freeform `availability` string (not numeric, not project-scoped — likely "full_time"/"part_time" or similar). `backend/apps/listings-service`'s `job-listing-budget.service.ts`'s `WorkSchedule` enum (`full_time`=40h/wk, `part_time`=20h/wk, `custom`) is a **per-task** assumption used only for budget math, not tied to any real user/team-member identity, and nothing anywhere cross-references a specific assignee's declared hours against the sum of hours assigned to them. `team.service.ts:113` even hardcodes `availability: null`. - **`listingType` is a fully unguarded, unrestricted string field (confirmed during PMCM-257, read-only)**: both `UpsertProjectDraftDto`/`CreateProjectDto`'s `listingType?: string` have only `@IsOptional() @IsString()` — not even an enum/`@IsIn(['project','service'])`. `updateProjectDraft` writes it unconditionally (`payload.listingType = dto.listingType`) with no branching and no side effects triggered elsewhere — switching a draft's offer type is already fully supported server-side with zero backend changes needed. `PhaseRepository.replaceForProject` also correctly wipes all existing phases/tasks when given `phases: []` (the delete step runs unconditionally on existing rows for that `projectId`, independent of what's in the new array) — so the frontend can safely clear a scope on an offer-type switch purely by sending an empty scope through the existing `PUT /publish/project/:id/scope` endpoint.
- **Correction: project-listing phase `phaseType`/`recurrenceSchedule`/`recurrenceCount` ARE already persisted (found during PMCM-257 follow-up, 2026-10-11 — corrects an assumption in the ticket that prompted this check, not a prior memory entry)**: `PhaseEntity` (`infrastructure/persistence/relational/entities/phase.entity.ts`) has real, nullable `@Column` definitions for all three; `CreateProjectPhaseDto` validates them (`@IsIn(['setup','recurring','ongoing'])`, `@IsIn(['weekly','monthly','quarterly'])`, `@Min(1) @Max(99)`); `PhaseMapper.toDomain`/`toPersistence` round-trip all three both ways; `publish.service.ts`'s `writeProjectScope` writes them into the `phaseRepository.replaceForProject` payload, and `normalizeServiceScope` (runs only when at least one phase carries a `phaseType` — pure project scopes "pass through untouched") re-orders setup-first/ongoing-last and server-side defaults `recurrenceSchedule ?? 'monthly'`/`recurrenceCount ?? 1` as a safety net independent of the frontend. `findOneWithTasks` (used by both `getProjectDraft` and `getProjectDraftBySlug`) returns `PhaseMapper.toDomain(entity)`, so a reloaded draft's `scope` array carries these fields too — full write/read round-trip confirmed by direct code read, not assumed. No migration needed for anything touching these three fields; they already exist and already work for project (not just job-listing) scopes.

- **Migration pattern bug found + fixed (PMCM-258, 2026-10-11)**: the older migration style used by `1783400000000-AddListingTypeToProject` and copied into this ticket's first draft of `1799000000000-AddPricingPeriodToProject` — `` DO $$ BEGIN ALTER TABLE "project" ADD COLUMN ... EXCEPTION WHEN undefined_table THEN NULL; END $$ `` — silently no-ops when the running connection's `search_path` doesn't include `listings` (confirmed: `typeorm-ts-node-commonjs query`'s own connection defaults to `"$user", public`; a bare `"project"` resolves to nothing, hits `undefined_table`, and the DO block swallows the error with zero signal — the migration still gets recorded as successfully executed in `listings.migrations` despite adding nothing). Caught only because the app then threw `column ProjectEntity.pricingPeriod does not exist` on boot. The newer migrations (`1795000000000-AddPublishedSnapshot`, `1796000000000-AddProjectTeamSizeDerived`, `1798000000000-AddPendingInviteEmails`) already use the correct, confirmed-working pattern — explicit `ALTER TABLE "listings"."project"`, no DO block, no exception-swallowing. `1799000000000-AddPricingPeriodToProject` was rewritten to match and re-ran clean after deleting its stale (no-op) `listings.migrations` row. **Open question, not re-investigated**: this casts doubt on whether `1783400000000-AddListingTypeToProject` itself ever actually ran its `ALTER TABLE` — `listingType` demonstrably exists and works in the DB today regardless, so either that migration got a different search_path at the time it first ran, or the column was added some other way. Anyone touching a `project`-table migration going forward should use the schema-qualified `"listings"."project"` form, never the bare/DO-block form.
- **`pricingPeriod` column added (PMCM-258, 2026-10-11)** — nullable `character varying(20)` on `listings.project`, via migration `1799000000000-AddPricingPeriodToProject`. The seller's saved Budget Calculator display-period preference (week/biweek/month/quarter/year); null means "no preference saved, caller picks a default." Three places needed the new column, not just the obvious one: (1) the publish module's `ProjectEntity`/`Project` domain interface/`ProjectMapper` (draft save/load path used by `my-listings` and the wizard); (2) `UpsertProjectDraftDto`/`CreateProjectDto` (`@IsOptional() @IsIn(['week','biweek','month','quarter','year'])`, the array exported as `PRICING_PERIODS` from `upsert-project-draft.dto.ts`); (3) **`src/projects/entities/project.entity.ts`** — a second, separate TypeORM entity class that also maps onto the same `{schema: 'listings', name: 'project'}` table, used by `ProjectsService.findBySlug`/`shapeProject` for the buyer-facing `GET /v1/projects/slug/:slug` response. Missing this second entity's column would have made the buyer page's "hydrate the period toggle from `project.pricingPeriod`" logic silently always no-op (the field would just never be in the response) despite the column existing and the publish-module side being fully wired — a trap worth remembering any time a `project`-table field needs to reach the buyer page, since that response goes through `projects.service.ts`'s `shapeProject`, not the publish module's mapper.
- **X1 override surface found in the legacy `/v1/projects` endpoints, not fixed (PMCM-258, 2026-10-11)**: `projects.controller.ts`'s `POST /v1/projects` and `PUT /v1/projects/:id` take `@Body() dto: Partial<Project>` — not a class-validator DTO, no decorators, no whitelist — and `projects.service.ts`'s `create`/`update` persist `dto.budget`/`dto.durationMonths` (and presumably anything else on the entity) verbatim with zero server-side override, the same class of bug found and fixed in the publish module's draft DTOs this same ticket. Confirmed via grep that no frontend code calls either endpoint (not `my-listings`, not the wizard, not `project-details`, not anywhere else in `frontend/`) — left unfixed because touching an endpoint with unknown real consumers (admin tool? mobile? truly dead?) without that context is riskier than the currently-unreachable-from-the-UI risk. Worth a dedicated look before this module is ever wired up to a live frontend flow.
- **X3 raw-internal-error leak fixed in the media-upload path (PMCM-261, 2026-10-14)**: `publish.service.ts`'s media-upload catch block (the function serving `POST /publish/media`) used to do `if (error instanceof Error && error.message) { throw new InternalServerErrorException(error.message); }` — any underlying driver/SDK error (TypeORM/Postgres error text, Cloudflare R2 SDK error, etc.) that wasn't already a deliberately-thrown `HttpException` had its raw `.message` placed directly into the 500 response body, which both editors' frontend error helpers then display straight to the user. Fixed to match the already-consistent safe pattern used elsewhere in this same file (`createProject`/`createProjectDraft`/the publish flow): `this.throwIfHttpException(error)` (re-throws only already-deliberate `HttpException`s) then a hardcoded generic `'Failed to upload media'`, no raw `error.message` ever reaches the body. Confirmed via a sweep of `publish.controller.ts`'s ~16 catch blocks and the rest of `publish.service.ts` that this was the only instance of this specific leak pattern — no global exception filter exists for listings-service at all (relies on Nest's default filter for truly-unhandled errors, which already sanitizes), so this one explicit `throw new InternalServerErrorException(error.message)` was the sole deviation.
