## Didit scanner integration — research + plan done, ZERO code written (2026-09-24)

Christopher's direction: use Didit (our existing vendor) first, keep our own custom camera screens (no Didit hosted UI), Hugging Face only as a last resort if Didit genuinely can't do something. Scanner implementation itself remains paused — this section is planning only, no files touched.

**Current code's real problem:** `document-verification-provider.interface.ts` / `didit-document-verification.provider.ts` (placeholder, POSTs to `/v1/sessions`) and the architecture described in Docs 01/05 are all built around Didit's **hosted Sessions API** (redirects user to Didit's own UI via `session_url`). That directly conflicts with "keep our own screens." The correct fit, confirmed against Didit's live docs, is Didit's **Standalone APIs** instead — synchronous multipart POSTs we call from our own backend after our own UI captures images:
- `POST /v3/id-verification/` — front/back image check, $0.15/check, returns `portrait_image`, quality scores, `mrz{}`, `warnings[]`.
- `POST /v3/face-match/` — selfie vs. reference portrait, $0.05/check, no liveness of its own.
- `POST /v3/passive-liveness/` — single static image, $0.10/check, spoof/deepfake detection.
- `POST /v3/database-validation/?services=<country>` — registry check, from $0.05/check, 60+ countries (coverage list not confirmed).

**Corrected plan (v2), after two rounds of user correction — key points, all verified against current Didit docs, not assumed:**
1. `save_api_request` (default `true`) DOES create a retrievable session + emit a `status.updated` webhook even on standalone calls — reversed an earlier wrong assumption that standalone = no webhook. Keep/adapt the existing webhook handler as a reconciliation path, do not retire it.
2. Live in-camera document detection inside our own custom UI: genuinely **unresolved** — no SDK/demo shows it, but "not documented" ≠ "not supported." Needs a direct question to Didit, tracked alongside the other open vendor questions in the Decision Record §7.1 register.
3. `useDocumentPresenceDetector` (fixed-region edge-density heuristic) stays unchanged and unreplaced — explicitly, this leaves the **face-as-document false-positive risk unfixed**: a face can trigger the same "document detected" green outline as a real ID. The outline is a capture-UI hint only, never evidence of a valid document. Only Didit's own captured-image result (after actual submission) can prove that.
4. Front/back/selfie/portrait linkage is **entirely our own responsibility**, not Didit's — Didit does not link standalone calls to each other. Design: take `portrait_image` from the id-verification response and pass it as `ref_image` into the face-match call; tag every call with our own `vendor_data` identifier; the real binding of "these calls = one attempt" lives only in our own DB row.
5. Reliability design for the new multi-call sequence (previously underspecified): persist an in-progress attempt row **before** the first Didit call (not after, like today), persist each call's result as it returns so a retry resumes only the incomplete calls (avoids re-billing completed ones), keep today's existing rule that a pure transport/infra failure never consumes one of the 3 user-facing attempts (only a real vendor decision does), and guard the start-verification endpoint against duplicate/concurrent submissions via the same advisory-lock pattern already used for duplicate-document blocking. Didit's actual failed-check billing policy is still an open vendor question (Decision Record §7.1) — now higher-stakes with 3-4 separate paid calls per attempt.
6. Registry validation (`/v3/database-validation/`) is explicitly included, feeding `VerificationDepth.REGISTRY_VALIDATED` per Decision Record §1.2's two-depth model — scoped to a small server-side country-coverage table we populate incrementally (starting with the template country), not attempted blindly for all countries since Didit's full coverage list isn't confirmed.
7. Existing 9-value status enum and both `IN_PROGRESS`/`PENDING` states are **preserved as-is**, not questioned or collapsed — `PENDING` gains real meaning (id-verification returned but face-match/liveness/registry still running) rather than being vestigial. Storage recommendation: extend (not replace) `pending_verification_sessions` with nullable per-call `request_id` columns (id-verification/face-match/liveness/registry) + a small cached-result field per call, created before the first Didit call fires; `VerificationAttempt` gets matching audit columns on finalize.

**Only 2 decisions genuinely block implementation** (everything else above is a recommendation, not a blocker): (a) `save_api_request=true` vs `false` — recommended `true` for the webhook/audit trail, needs confirmation; (b) where the selfie/portrait image reference is stored — on `IdentityDocument` directly, or a separate entity. Everything else (webhook handling, linkage mechanism, retry/idempotency design, registry scoping, storage columns) has a concrete recommended design already, per the corrected plan above.

**Not yet done:** turning this plan into actual code — no interface changes, no new entity columns, no migration, no provider rewrite, no frontend selfie-capture screen (confirmed via grep: no selfie/face-match capture screen exists anywhere in the frontend today despite being in the design). Waiting on user review/approval of the plan before any of that starts.

## Travel duration "Skip" (PMCM-639) — known backend limitation
- The backend cannot represent a Travel Mode with no duration. `declared_duration = null` ("skipped" in the Data Model doc, AC-05.4) on an active period is the fail-closed `invalid` state in `common/travel-mode/travel-mode-state.ts` (pinned by `travel-mode-state.spec.ts`: "raw active, missing duration"), and `TravelDurationRequestDto.duration` is a required enum with no skipped value (Doc 05 flags this DTO gap). The length of a skipped period is documented nowhere.
- So the frontend's Skip sends an explicit `not_sure` (`SKIPPED_TRAVEL_DURATION_LABEL`, `frontend/src/lib/api/travel-mode-backend.ts`), ignores any earlier selection, and keeps "skipped" as screen state only, to choose the "Travel Mode is now active!" copy. Skip and "Not sure" are indistinguishable server-side, and a page refresh cannot recover which one was used.
- A real skipped state needs a backend contract decision (optional DTO field plus a skipped marker/period length, touching expiry, reminders, check-in and the CAS write) — not made here.

## Didit callback origin (PMCM-636/639 staging QA)
- `FRONTEND_URL` is a comma-separated list of every frontend origin the shared backend serves (render.yaml: live, staging, dev, localhost), not one URL. Using it whole as Didit's `callback` made `POST /v3/session/` fail with HTTP 400 (`InvalidSessionCreationRequestError` -> 502 `VENDOR_STAGE_UNAVAILABLE`).
- `common/config/frontend-origin.ts` resolves it: the browser sends its own origin as optional `returnOrigin` on `kyc-sessions` and `kyc-sessions/home-country-change` (the gateway does not forward `Origin`, and `proxy.service.ts` is login-protected); it is accepted only if it exactly equals a configured origin, else 400 `INVALID_RETURN_ORIGIN`. Several origins configured and none sent -> 400 `RETURN_ORIGIN_REQUIRED` (never "the first one", which would send staging users to production). One configured origin works without it (local). Nothing configured -> `free_kyc_not_configured` as before.
- Both routes now run the DTO through the global ValidationPipe (`forbidNonWhitelisted`): a body with any other field is a 400, where it used to be ignored.
- Deploy order: backend can go first (the old frontend's `{}` body still works for a single configured origin, but with the multi-origin list it needs the new frontend to send `returnOrigin`). Ship both together.
