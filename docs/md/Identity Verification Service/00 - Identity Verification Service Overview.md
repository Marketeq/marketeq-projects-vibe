# __1\. Service Purpose__

The Identity Verification backend capability exists to establish and maintain two independent, ongoing facts about a platform account before granting full access: where the user is \(their home country and current location\) and who the user is \(their legal identity, established through a government\-issued document and a biometric/facial check, both performed within a single verification\-vendor session\)\. Together these determine whether an account is treated as verified, temporarily traveling, or unverified — a status other parts of the platform read to allow or block specific actions \(00 — Epic Overview §1, §5\.12\)\.

This is confirmed backend work: no dedicated identity\-verification or KYC capability exists among the services described in the Marketeq Core Backend Technical Architecture Overview, and none of the Authentication, User, or Notifications Service documentation reviewed contains identity\-document, travel\-mode, or biometric\-consent logic \(00 — Epic Overview §6\)\. The purpose of this capability is therefore to provide that missing logic and state\.

# __3\. Core Responsibilities__

__1\. Location detection & home\-country confirmation — __process a detected current location and a user's confirmation of it as home country \(00 — Epic Overview §5\.1\)\.

__2\. Travel/Relocation classification — __record a binary classification \(Temporarily Traveling or Permanently Relocated\) when a user declines their detected location as home country; there is no third option \(location\-verification\-two\-decisions\.md, Item 2\)\.

__3\. Travel Mode state management — __for Temporarily Traveling only: capture declared duration, activate/maintain Travel Mode, and run the decided re\-prompt cadence \(daily re\-check plus every fresh login; immediate re\-prompt on any new detected\-country change; skip\-reminders at 3 and 7 days, then stop; first prompt fires roughly 5 minutes after a user first reaches the home page\) \(Build Spec, Q1–Q2 decisions\)\.

__4\. Permanent\-relocation handling — __route a Permanently Relocated classification back through location/document proof verification rather than duration selection or Travel Mode, since a relocation claim must be proved by a document before it replaces the verified home country \(location\-verification\-two\-decisions\.md, Item 2 update; 00 — Epic Overview §5\.3\)\.

__5\. Document intake — __receive and store document type, issuing country, document number, expiration date, issuing state \(for licenses\), and document images from both the scan\-capture path and the manual\-entry fallback path\. __6\. OPEN\-01 is resolved \(Decision Record §2, §5 Q4\)\.

__7\. Expired\-document rejection — __reject a manually entered document at the point of submission if its expiration date is in the past; expired documents are also not accepted at onboarding through the vendor\-driven scan path \(Build Spec, Q12 decision; Decision Record §5, Q2\)\.

__8\. Automated scan\-decisioning with a three\-attempt retry limit — __apply a three\-attempt limit on verification attempts \(revised from an earlier ten\-attempt figure\)\. __9\. Verification status tracking — __maintain identity verification status and location verification status as two independently satisfiable conditions\. # __4\. Key Workflows__

- First\-time location verification: detect location → user confirms as home country → proceed to document type selection \(00 — Epic Overview §5\.1, §5\.4\)\.
- Travel/Relocation classification: user declines detected location as home country → classify as Temporarily Traveling \(duration capture, Travel Mode activation, reminder cadence\) or Permanently Relocated \(routes into the document\-based verification workflow below, no Travel Mode\) \(Build Spec Q1–Q2; location\-verification\-two\-decisions\.md, Item 2\)\.
- Document\-based identity verification: document type/issuing\-country selection → capture \(webcam or mobile QR handoff, still per the existing frontend design\) → the selected vendor \(Didit\) authenticates the document via its own fallback chain \(barcode, MRZ, NFC, OCR\) plus, where available, government\-registry validation → success, or failure routed to Rescan or Enter Manually, up to a three\-attempt limit → a rejection beyond that limit is final this sprint, with no escalation path \(00 — Epic Overview §5\.4–§5\.8; Decision Record §1\.2, §1\.3, §2\.2, §6\.1\)\.
- Verification depth: depending on what the vendor supports in the user's country, a submission is either Registry Validated \(checked against the issuing government's own data source\) or Authenticated \(barcode/MRZ/NFC/OCR plus tamper detection and face match with liveness, no registry lookup\) — both count as fully verified \(Decision Record §1\.2\)\.
- Vendor\-bundled face match: face match and liveness now run within the same Didit session as document verification, rather than as a separate Persona hand\-off\. How this changes the existing “ID not verified” gating\-modal flow shown in the Figma exports is not yet reconciled and remains an open design item \(Decision Record §4, §7\.3\)\.
- Returning\-user re\-verification: a user logging in from a location other than their confirmed home country is re\-shown the home\-country confirmation; confirming re\-runs country/document selection and capture \(00 — Epic Overview §5\.10\)\.
- VPN/proxy detection and blocking: VPN, Proxy, or VPN & Proxy is detected and interrupts use with a Dismiss/Reload modal; verification cannot complete while a VPN is detected\. \(Decided behavior; the detection mechanism itself does not exist in the codebase yet — Build Spec Q6, “Build gap\.”\)
- Verification status exposure for action\-gating: other parts of the platform read identity and location verification status independently to gate specific actions \(00 — Epic Overview §5\.12; 01 — FEAT\-39/FEAT\-40\)\.
- Duplicate\-document blocking: a document submission already associated with a different account is deterministically blocked \(not an AI review case\); the submitting user is told an account already exists and is pointed to account recovery \(Decision Record §5, Q7; §6\.1\)\.
- Internal\-team review: internal staff can review a user's verification status and submitted identity documents \(mechanism undefined\)\. This is separate from the verification\-decision pipeline itself, which now has no manual\-review step \(Decision Record §1\.3\)\. \[Superseded, 18 September 2026: the "mechanism undefined" framing and the implication that submitted identity documents are internally reviewable are superseded — Doc 02 SVC\-24 / TRVG2 §6\.1 / Christopher's Answer 4 confirm a read\-only internal status endpoint exposing only status, attempt\_count, timestamps, and a coarse failure reason, with no document access\. See §9 System Boundaries below for the fuller correction\.\]
- Notification triggering: verification/travel\-related events are emitted for downstream delivery via the Notifications Service \(00 — Epic Overview §5\.11, §7\.3\)\.

# __5\. Primary Entities__

- Home Country / Location — a verified home country \(document\-proved, persists until the detected country changes\) held distinctly from current detected location \(a continuous signal\) \(Build Spec, “The model”\)\.
- Travel/Relocation Declaration — classification \(Temporarily Traveling / Permanently Relocated\), declared duration \(temporary travel only\), Travel Mode active flag\.
- Document Submission — document type, issuing country, document number, expiration date, issuing state \(licenses only\), capture method \(scan or manual entry\), document image reference, verification depth achieved \(Registry Validated or Authenticated\)\.
- Identity Verification Status — extensible status/level field \(not boolean\): Not Verified / Submitted\-Pending Review / Verified / Rejected\-blocked, tracked independently of location \(Decision Record §5, Q8\)\.
- Location Verification Status — Not Verified / Submitted\-Pending Review / Verified, tracked independently of identity\.
- Verification Attempt/Audit Record — verification\-vendor session ID, timestamp, method, document type, outcome, failure code, attempt count \(against the three\-attempt limit\)\.
- Duplicate\-Document Block — a deterministic block raised when a submitted document is already on file against a different account; the submitting user is told an account exists and is pointed to recovery \(resolves UX\-03\)\.
- Notification Event — a verification\- or travel\-related occurrence \(Travel Mode activated, submitted for review, verified, home country updated\) consumed by the Notifications Service\.

# __6\. States__

- Identity Verification Status: Not Verified → Submitted/Pending Review → Verified, modeled as an extensible field rather than a boolean \(Decision Record §5, Q8\)\. - Location Verification Status: Not Verified → Submitted/Pending Review → Verified — tracked and transitioned independently of Identity Verification Status \(01 — FEAT\-40; 00 — Epic Overview §5\.12\)\.

# __7\. Integrations__

- Didit \(third\-party, selected verification vendor — Decision Record §2\): a single hosted/API session providing document verification, liveness, and face match together, plus government\-registry validation where the vendor holds a data source for that country\. Covers 220\+ countries, 14,000\+ document types, and holds SOC 2 Type I/II, ISO/IEC 27001:2022, GDPR, HIPAA, eIDAS 2\.0, and other certifications \(Decision Record §2\.3\)\. This service consumes vendor sessions and verifies HMAC\-signed webhooks rather than polling \(Decision Record §6\.2\)\. No biometric data is stored by this service; it remains with the vendor\. Didit is an early\-stage company \(recent $7\.5M seed round\); data portability and exit terms are noted as unconfirmed \(Decision Record §2\.4\)\. Nine vendor/engineering/design questions remain outstanding and do not block this document \(Decision Record §7\)\.
- Authentication Service \(auth\-service\): owns login/session issuance \(JWT, cookie\-based sessions\); the natural integration point for login\-time verification\-status checks, though no such check exists there today — this would be new capability \(00 — Epic Overview §6\.1\)\.
- User Service \(user\-service\): already exposes location/timezone endpoints \(PUT /users/:id/location, GET /location/countries, GET /location/cities, PUT /users/:id/timezone\) and MaxMind GeoLite2\-based IP resolution — the closest existing infrastructure match for location detection, though documented around timezone rather than home\-country/travel status \(00 — Epic Overview §6\.2\)\.
- Notifications Service \(notification\-service\): the existing RabbitMQ\-consumed, Ably/SendGrid\-delivered, per\-user/per\-category notification pipeline this epic's alerts would route through, per Epic Overview §6\.3\. Its documented default categories \(messages, projects, reviews, account, teams\) do not currently include a verification\-specific category\. How verification/travel events will integrate with this pipeline is not decided and is left for later documentation\.
- Location Service \(planned, separate initiative\): location\-service\-migration\-plan\.md specifies a new service exposing two distinct endpoints — coordinate\-based precise location \(profile display\) and IP\-based country resolution \(verification/currency/timezone\) — to replace today's duplicated, independently\-drifting location logic in user\-service and earnings\-service\. This is a companion effort with its own phased migration plan\. Whether, or how, the Identity Verification capability integrates with this planned Location Service is not established by any source and is not decided here\.
- Not integrated: wire\-review\-service's EDD/OFAC compliance checks — no source connects them to this capability \(00 — Epic Overview §9\)\.
