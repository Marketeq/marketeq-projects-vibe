__Primary Sources: __00 — Identity Verification Service Overview; 01 — Identity Verification Technical Architecture; 00 — Identity Verification Epic Overview; 01 — Identity Verification Feature List \(SOP A, frontend\); Identity Verification Decision Record \(31 August 2026\); Marketeq Core Backend Technical Architecture Overview\.

Frontend FEAT\-IDs \(SOP A\) are cited where a backend feature exists because of a frontend requirement\. Frontend behavior itself — screens, layout, copy, capture UI — is out of scope here\.

# __Key Workflows \(Backend Perspective\)__

- __Location/home\-country confirmation: __LocationProvider resolves country\-level signal → orchestration processes user confirmation → verified home country persisted \(00 §4; 01 §11\)\.
- __Travel/relocation branch: __classification recorded → Temporarily Traveling enters duration capture \+ Travel Mode \+ reminder cadence; Permanently Relocated routes back into document/location proof verification, not Travel Mode \(00 §4; location\-verification\-two\-decisions\.md, Item 2\)\.
- __Document \+ biometric verification: __intake \(type/country/number/expiration/image\) → a single Didit vendor session performs document authentication \(registry\-validated or authenticated depth\), liveness, and face match together, up to a three\-attempt limit → Identity Verification Status transitions; a rejection beyond the limit is final this sprint, with no escalation path \(Decision Record §1\.2, §1\.3, §2, §6\.1\)\.
- __Duplicate detection: __incoming document compared against previously stored submissions → a match is a deterministic block, not an AI review case; the user is told an account exists and is pointed to recovery \(Decision Record §5 Q7, §6\.1; resolves UX\-03\)\.
- __Status exposure: __other services read Identity/Location Verification Status via REST; this service publishes RabbitMQ events on state changes, and separately consumes the vendor's own result via an inbound HMAC\-signed webhook \(01 §5, §10\)\.

# __A\. Location Verification Orchestration__

__SVC\-01 — Location Signal Consumption via LocationProvider\. __Consumes country\-level location resolution through the LocationProvider interface; does not implement IP geolocation itself \(01 §11\)\.

__SVC\-02 — Home\-Country Confirmation Processing\. __Processes a user's confirmation of a detected location as home country \(00 §3 item 1; Epic Overview §5\.1\)\.

__SVC\-03 — Verified Home\-Country Persistence\. __Maintains a verified home country distinct from the continuous current\-detected\-location signal; persists until the detected country changes \(00 §5, “Home Country / Location”\)\.

__SVC\-28 — Returning\-User Re\-Verification Trigger\. __Re\-triggers home\-country confirmation when a user logs in from a location other than their confirmed home country; confirming re\-runs country/document selection and capture\. Not scoped to Travel Mode — applies independently of it \(00 §4; Epic Overview §5\.10\)\.

# __B\. Travel & Relocation Classification__

__SVC\-04 — Travel/Relocation Classification Recording\. __Records a binary classification \(Temporarily Traveling / Permanently Relocated\) when a user declines the detected location as home country; no third option \(00 §3 item 2\)\.

__SVC\-05 — Travel Duration Capture & Travel Mode Activation\. __Captures declared duration \(Temporarily Traveling only\) and activates Travel Mode \(00 §3 item 3\)\.

__SVC\-06 — Travel Mode Reminder Scheduling\. __Applies only while a user is already classified Temporarily Traveling \(Travel Mode active\)\. Runs the confirmed re\-prompt cadence: daily re\-check plus every fresh login, immediate re\-prompt on a new detected\-country change, skip\-reminders at 3 and 7 days then stop, first prompt ~5 minutes after first reaching the home page \(00 §3 item 3, “for Temporarily Traveling only”; Build Spec Q1–Q2\)\. Distinct from the general Returning\-User Re\-Verification trigger \(SVC\-28\), which is not Travel\-Mode\-scoped\.

__SVC\-07 — Permanent\-Relocation Routing\. __Routes a Permanently Relocated classification back through location/document proof verification rather than duration selection or Travel Mode \(00 §3 item 4\)\.

# __C\. Document Intake__

__SVC\-08 — Document Submission Intake\. __Receives and stores document type, issuing country, document number, expiration date, issuing state \(licenses\), and document image reference, from both scan and manual\-entry paths \(00 §3 item 5\)\.

__SVC\-09 — Document\-Type Enum Management\. __Maintains the document\-type set per Christopher’s confirmed Answer 7 \(17 September 2026\), which corrects the modeling this feature previously described: one shared document\_type value — passport, ID card, driver’s licence, residence permit — subject to per\-country availability determined entirely by Didit, the selected vendor, across the 220\+ countries it supports; no country list is maintained on our side\. A new document\_type\_label field \(display\-only, may vary by locale\) carries user\-facing wording without moving the stored enum value \(Doc 03 §6a; TRVG2 §1\.4\)\. Birth Certificate remains excluded; Health Insurance Card, Tax Card, and Social Security Card are available from the vendor but are not in scope \(Decision Record §3\.2\)\. \[Superseded, 17 September 2026: earlier drafts of this feature, following Decision Record §3’s “must be preserved in our own data model if required” framing, described National ID and Identification Card as two distinct stored types\. __SVC\-10 — Country\-Dependent Field\-Requirement Structure\. __Applies which document fields are required vs\. optional per document type/issuing country as a structural \(schema\-level\) concern\. Per\-country availability is fully determined by Didit, the selected vendor — no per\-country requirement definition is authored or maintained by this service \(Decision Record §5, Q4\)\. This is distinct from SVC\-13's content\-validation logic\.

# __D\. Manual\-Entry & Validation__

__SVC\-11 — Manual\-Entry Fallback Intake\. __Accepts manually entered document data as a fallback to scan capture, for the same document\-type set as SVC\-09 \(00 §3 item 5; SOP A FEAT\-30\)\.

__SVC\-12 — Expired\-Document Rejection at Submission\. __Rejects a manually entered document at the point of submission if its expiration date is in the past; expired documents are also not accepted at onboarding through the vendor\-driven scan path \(00 §3 item 7; Build Spec Q12; Decision Record §5, Q2\)\.

__SVC\-13 — Manual\-Entry Validation Orchestration \(OPEN\-01 Resolved\)\. __Delegates country\-dependent content validation to Didit, the selected DocumentVerificationProvider implementation — no per\-country validation rule set is authored or maintained by this service \(00 §3 item 6; 01 §10; Decision Record §2, §5 Q4\)\.

# __E\. Automated Scan Decisioning__

__SVC\-14 — Automated Scan Decision Orchestration\. __Orchestrates the confirmed automatic accept/reject outcome on each document\-scan attempt via the DocumentVerificationProvider boundary, now backed by Didit \(01 §10\)\. The Decision Record confirms this explicitly: no manual review of any kind — the AI reviewer's decision is final apart from retry \(00 §3 item 8; Decision Record §1\.3\)\. This service does not itself implement the document\-authentication/validation logic producing that outcome — that remains owned by Didit \(01 §3\)\.

__SVC\-15 — Scan\-Attempt Retry Limit\. __Enforces a three\-attempt limit on scan attempts, revised from an earlier ten\-attempt figure; a rejection beyond that limit is final this sprint, with no escalation path \(00 §3 item 8; Decision Record §1\.3, §6\.1\)\. This corresponds to the FAILED\_FINAL state in TRVG2 §1\.1 \(“Verification status”\) \[Citation corrected 21 September 2026; formerly cited as Technical Requirements — Verification Gates §1\.2, “Status enumeration”\]\. Per TRVG §8\.1 \(“Terminal states have no outbound transition”\), whether FAILED\_FINAL remains permanently terminal or eventually supports a path out is an unresolved product decision — TRVG records three options without selecting one\. No recovery path is asserted here\. \[Superseded, 18 September 2026: TRVG2 §2\.9/§3 resolves this — FAILED\_FINAL is not permanently terminal; it clears automatically after a 24\-hour cooldown, resetting attempt\_count to 0 and status to UNSTARTED, with no human or support action required\. This SVC\-15 body's "unresolved product decision" framing and "no escalation path" characterization above are superseded by that automatic\-clearing behavior \(see SVC\-18, which already states this correctly\)\.\]

# __F\. Duplicate\-Document Detection__

__SVC\-16 — Duplicate/Reused\-Document Match Detection\. __Compares an incoming document submission against previously stored submissions this service already holds, to detect reuse across accounts \(01 §14\)\. The Decision Record confirms this is a deterministic check — “no AI evaluation required” — though the exact underlying match technique \(exact match vs\. similarity matching\) is still not decided by any source \(Decision Record §6\.1\)\.

__SVC\-17 — Duplicate\-Document Deterministic Block \(Resolved — UX\-03\)\. __Blocks a submission when a match is found, rather than merely flagging it\. The submitting user is told an account already exists and is pointed to account recovery; the block is a fixed rule, not an AI review case\. This resolves UX\-03, previously an undefined flag with no automatic consequence \(Decision Record §5, Q7; §6\.1; 00 §3 item 10; 01 §14\)\. Per Technical Requirements — Verification Gates §6\.1 \(“Account enumeration”\), the block response must not identify the account holding the conflicting document — not its email address, a masked address, a profile name, or a handle; the response states only that the document is in use\. The submission endpoint must be rate\-limited so repeated submissions cannot be used to probe which documents exist in the system\.

# __G\. Verification Status Tracking__

__SVC\-18 — Identity Verification Status State Machine\. __Tracks Identity Verification Status, modeled as an extensible enumeration rather than a boolean \(Technical Requirements — Verification Gates 2 \(“TRVG2”\) §1\.1, “Verification status”\), using the same nine\-value enumeration TRVG2 carries forward from the original TRVG §1\.2: UNSTARTED, IN\_PROGRESS, PENDING, VERIFIED, FAILED, FAILED\_FINAL, BLOCKED\_DUPLICATE, BLOCKED\_AGE, EXPIRED\. Transitions per TRVG2 §3 \(“State Transitions”\): UNSTARTED → IN\_PROGRESS \(session created\) → PENDING \(submitted to vendor\) → VERIFIED \(vendor approves\); from PENDING, status may instead transition to FAILED \(vendor rejects, attempt\_count < 3\), FAILED\_FINAL \(vendor rejects, attempt\_count = 3\), BLOCKED\_DUPLICATE \(duplicate document\_ref detected\), or BLOCKED\_AGE \(document indicates under 18\)\. FAILED returns to IN\_PROGRESS on a new session \(retry\)\. VERIFIED transitions to EXPIRED when document\_expires\_on is reached; EXPIRED returns to IN\_PROGRESS on a new session and, on vendor approval, restores to VERIFIED\. attempt\_count increments on transition into FAILED \(not on session creation\), resets to 0 on transition into VERIFIED, and is confirmed account\-wide rather than per\-document \(SVC\-15 cross\-reference; TRVG2 §2, gate table note\)\. This corrects the “unresolved” framing this feature previously carried per original TRVG §8\.1/§8\.2: FAILED\_FINAL now clears automatically after a 24\-hour cooldown interval, and BLOCKED\_AGE now clears automatically when the newly introduced eligible\_on date \(the date the holder turns 18, derived from the document at read time and then discarded — no date of birth is held on the account\) is reached \(TRVG2 §3\)\. BLOCKED\_DUPLICATE remains a deliberate, non\-clearing block — one account per person — and is not affected by either change\. Separately, a verified account whose document expires does not lose gate access immediately: gate evaluation \(SVC\-20\) checks is\_verified\(\) OR in\_grace\(\), and in\_grace\(\) holds for 30 days from the newly introduced expired\_at timestamp regardless of the EXPIRED status value \(TRVG2 §1\.1, §2\)\. This feature and 01 — Technical Architecture should be updated together to reflect this same state model \(00 §6; SOP A FEAT\-40\)\.

__SVC\-19 — Location Verification Status State Machine\. __Tracks Location Verification Status independently of Identity Verification Status — never combined into one flag\. TRVG2 §1\.1 confirms location\_status uses the same nine\-value enumeration as identity\_status, consistent with the original TRVG §1\.2\. TRVG2 §1\.3 \(“What location verification establishes”\) substantially narrows — though does not verbatim resolve — the previously open transition\-scope question: location\_status verifies permanent residence, not physical position; a verified account holder found in a different country remains verified \(no gate closes on a network signal alone\), and a detected residence mismatch is resolved only by re\-verifying with a document for the new country — never by a network reading resolving on its own\. This confirms location re\-verification follows the same document\-verification transition path as identity verification \(submitted → vendor decision → VERIFIED/FAILED, etc\.\), even though TRVG2 does not restate §3’s transition table in location\-specific wording\. Travel Mode is formalized as a prompt\-suppression mechanism only \(TRVG2 §1\.3\): it does not set, satisfy, or substitute for location\_status, and does not open or close any gate — it only suppresses re\-verification prompts for a stated period\. Whether every one of the nine enumeration values \(e\.g\., BLOCKED\_DUPLICATE, BLOCKED\_AGE\) is reachable for a location verification specifically remains unaddressed by any source and is not assumed here \(00 §6; 01 §2; SOP A FEAT\-40, FEAT\-39 modal variants\)\. \[Updated 21 September 2026: Doc 03’s 21 September update proposes a more specific answer — seven of the nine values, excluding BLOCKED\_AGE and EXPIRED, are proposed as reachable for location\_status — an engineering decision made under Christopher's SOP guidance \(five\-question technical resolution, Q1\)\. EXPIRED itself is explicitly left unresolved: TRVG2’s shared enumeration implies location\_status could reach it, but the Location Verification Build Specification states a verified home country never expires, with no document\-validity requirement or re\-verification timer\. This is a genuine, unresolved conflict between the two sources, not decided by this document — tracked in the Unresolved Questions register, item 6 \(Doc 03 Section 6a, Section 10\)\.\]

__SVC\-20 — Verification Status Exposure via REST\. __Exposes both status values, and the gate predicate computed from them, over synchronous REST for other platform services needing an immediate answer at the moment of a gated action\. TRVG2 §2 redefines the predicate this service exposes: is\_verified\(account\) := identity\_status == VERIFIED AND location\_status == VERIFIED; in\_grace\(account\) := expired\_at is set AND fewer than 30 days have elapsed since it; gate\_open\(account\) := is\_verified\(account\) OR in\_grace\(account\)\. This replaces the earlier is\_verified\(\)\-only predicate and the profile\.completeness\-dependent in\_marketplace\(account\) condition entirely — profile completeness no longer participates in gating at all, superseding this feature’s earlier statement that in\_marketplace\(account\) is out of this service’s scope\. This service does not itself enforce any of the nine gates now defined \(G1–G9, TRVG2 §2\) — enforcement belongs to each action’s own endpoint \(TRVG2 §2\.3, “Conditions, not mechanisms”\), consistent with the boundary established in 00 items 15–16 and 01 §2\. \[Superseded, 17 September 2026: earlier drafts referenced gates G1–G6 and an in\_marketplace\(account\) condition requiring profile\.completeness; TRVG2 removes profile completeness from the model entirely and expands the gate list to nine — G1 marketplace discovery, G2 publish any listing, G3 apply for a job, G4 receive/accept an offer, G5 client\-facing roster, G6 owner management view, G7 accept an invitation, G8 log time, G9 withdraw earnings — see Doc 03 update note and TRVG2 §2\.\] Data returned through this REST surface remains scoped per consumer type, per TRVG2 §6 \(“Data Exposure”\): verification internals must never reach a client\-facing consumer, as an API contract requirement rather than a presentation concern\. A hiring client may receive only whether the hire action is open or closed — never the status value, failure reason, attempt\_count, age block, duplicate block, document data, or the reason a profile is unhireable\. A team owner may receive each member’s gate result and a coarse state indicator — never member documents, failure reasons, attempt\_count, or date of birth\. The account holder may receive their own status and remaining attempts — never raw vendor payloads or document\_ref\. The calling services themselves are not enumerated by any source and are not invented here \(01 §5; SOP A FEAT\-39\)\.

# __H\. Verification\-Vendor Coordination \(Didit\)__

__SVC\-21 — Verification\-Vendor Session Initiation\. __Initiates a Didit verification session — covering document verification, liveness, and face match together in one session — replacing the earlier separate Persona hand\-off model \(Decision Record §2, §4\)\. Document verification is expected to come before face match within that session, though this ordering is explicitly marked Open pending confirmation against the design files \(Decision Record §4 table; §7\.3, Q8\) — effectively carrying forward OPEN\-04, not resolving it\. How this changes the existing frontend gating\-modal condition \(previously: hand off when location is verified but identity is not\) is an open design item \(Decision Record §7\.3, Q9\)\.

__SVC\-22 — Verification\-Vendor Boundary Enforcement\. __Confirmed boundary: face match and liveness are provided entirely by Didit, the selected vendor, bundled into the same session as document verification \(Decision Record §2, §4\) — superseding the earlier Persona\-specific boundary\. This service stores no biometric data — Didit retains it under its own policy — and does not expand the vendor's role beyond document verification, liveness, and face match \(01 §9\)\.

# __I\. Audit & Attempt History__

__SVC\-23 — Verification Attempt/Audit Logging\. __Records the verification\-vendor \(Didit\) session ID, timestamp, method, document type, outcome, and failure code for each verification attempt, server\-side only, nothing user\-facing; attempt counts are tracked against the three\-attempt retry limit \(00 §3 item 12; Decision Record §6\.1, §6\.2\)\.

# __J\. Internal\-Team Review Access__

__SVC\-24 — Internal Review Data Access Surface \(Under Review\)\. __Supports a read\-only internal endpoint exposing verification status, attempt\_count, timestamps, and the coarse failure reason, per Christopher’s confirmed Answer 4 \(17 September 2026\) and TRVG2 §6\.1 \(“Internal and support access”\)\. # __N\. Vendor Session & Webhook Handling__

__SVC\-30 — Vendor Webhook Consumption \(HMAC\-Signed\)\. __Consumes Didit verification\-session results via inbound, HMAC\-signed webhooks rather than polling the vendor \(Decision Record §6\.2\)\. Per TRVG2 §5 \(“Vendor Integration”\): webhooks may be redelivered, so status updates must be idempotent on vendor\_session\_id; and a vendor outage must leave status unchanged rather than transitioning affected accounts to FAILED, distinguishing vendor unavailability from vendor rejection\.

__SVC\-31 — Verification Depth Tracking\. __Records which verification depth a submission achieved — Registry Validated \(checked against the issuing government's own data source\) or Authenticated \(barcode/MRZ/NFC/OCR plus tamper detection and face match with liveness, no registry lookup\) — both counting as fully verified \(Decision Record §1\.2\)\.

__SVC\-33 — Document Deletion on Account Deletion\. __Deletes identity documents when the associated account is deleted; no AML\-style retention obligation applies given the product's confirmed non\-regulated status, though general data\-protection obligations still apply \(Decision Record §5, Q5; Regulatory Status\)\.

# __Explicitly Not This Service's Features__

Per 00 §2 \(Out of Scope\) and 01 §3 \(Responsibilities Explicitly NOT Owned\), the following belong to other services or providers and are referenced above only where they create a direct requirement on this service:

- Facial/biometric capture, matching, or storage — Didit, the selected verification vendor \(replacing the earlier Persona boundary\)\.
- Document\-authentication/validation logic itself — Didit, the selected vendor\.
- Precise, coordinate\-based location for profile display — user\-service today, planned Location Service eventually\.
- Login/session issuance — auth\-service\.
- Notification delivery mechanics \(Ably/SendGrid dispatch, preferences, unread counts\) — notification\-service\.
- The gated actions themselves \(apply to a job, join a team, publish a job, log time\) — their owning epics/services\.
- Payment\- or compliance\-specific verification \(e\.g\., wire\-review\-service's EDD/OFAC checks\) — not connected by any source\.
- Admin\-facing review/approval/override UI, roles, or permissions — not defined by any source \(SVC\-24 covers only the technical access surface, not this\); no manual review or override capability of any kind exists this sprint regardless \(Decision Record §1\.3\)\.
- Help desk/escalation design for failed or rejected verifications — explicitly out of scope this sprint; no design exists \(Decision Record §1\.3, §8\)\.
