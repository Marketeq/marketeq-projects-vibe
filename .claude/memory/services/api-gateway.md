## What This Service Does
- Single public HTTP entry point for the platform (`apps/api-gateway`) — all external traffic from the frontend, mobile app, and desktop app hits this service first.
- Owns global body-parsing, including a raw-body capture path for `/v1/webhooks/*` and `/api/v1/webhooks/*` so Stripe/Ramp webhook signature verification gets byte-for-byte original request bodies.
- Owns CORS policy (`FRONTEND_URL` allow-list plus a regex allow-list for Vercel preview deployments; localhost origins are dropped in production and preview matches are logged — see Key Decisions).
- Owns the CSRF origin check (`src/middleware/csrf-origin.middleware.ts`), duplicated in auth-service.
- Owns request rate limiting for all external traffic (`src/rate-limit/`), in monitor mode until enforcement is enabled. See Key Decisions.
- Proxies requests through to the internal microservices (see `proxy.service.ts`).
- Runs three RabbitMQ microservice consumers for CMS cache-invalidation events.

## Key Decisions
- **Added Helmet security headers (2026-09-16), Security Tasklist item #4.** Helmet was a declared dependency used in only 2 of ~28 services (`portfolio-service`, `time-tracking-service`) and missing from api-gateway, the one service that terminates all external browser traffic. Added `helmet` (`^7.0.0`, matching the version already in use elsewhere) to `apps/api-gateway/package.json`, and wired `app.use(helmet())` into `src/main.ts` immediately after app creation, before body-parsing/CORS, so headers apply to every response including error responses from `GlobalExceptionFilter`.
- **Used bare `helmet()` defaults, not a custom CSP.** api-gateway also handles Stripe/Ramp webhook verification and OAuth popup flows (Google, LinkedIn, Wise, Payoneer) — the highest-blast-radius service to get a hardening change wrong on. Two other services already run bare `helmet()` in production without documented issues, so that proven pattern was matched instead of writing a bespoke policy for the highest-traffic entry point. Verified with `npx nest build api-gateway` (clean) and confirmed the compiled `dist/apps/api-gateway/main.js` actually calls `helmet()`.
- Full rollout status across the rest of the platform is tracked separately in `docs/md/CyberSecurity/HTTP Security Headers (Helmet) — Rollout Status.md`, not duplicated here.
- **Added rate limiting (2026-09-22), Security Tasklist (Revised) item #5.** New `src/rate-limit/` module, in two stages: per-IP limiting wired in `main.ts` with `app.use()` (after helmet and CORS, before body parsing — moved there 2026-09-25, see gotchas; keyed by client IP: general, login, password reset, 2FA verify, 2FA/SMS send, username check, webhooks) and `PostAuthRateLimitMiddleware`, module middleware after `JwtMiddleware` (keyed by the verified user id: general per-user, money-service writes, gateway uploads). Two stages because a single pre-JWT limiter has no verified user to key on, and a single post-JWT limiter never counts requests `JwtMiddleware` rejects.
- **Counters in the existing Redis (`REDIS_URL`) via `ioredis`, no new dependency.** One atomic Lua script per hit (INCR + PEXPIRE). Falls back to an in-memory store when Redis is unset or unreachable; requests never wait on Redis (offline queue off, 250 ms command timeout).
- **Ships in monitor mode** (`RATE_LIMIT_MODE` unset = `monitor`): over-limit requests are logged once per key per window as `WOULD_BLOCK` and still served. `enforce` returns 429; `off` disables it. All limits are env-tunable (`RATE_LIMIT_<RULE>_LIMIT` / `_WINDOW_SEC`).
- **429 body uses `GlobalExceptionFilter`'s shape** (`{ statusCode, code: 'RATE_LIMITED', message, details: { retryAfterSeconds } }`) plus `Retry-After`, written directly (not thrown) so floods don't add one filter error log per request. No existing status code or error shape changed.
- Full rules table, configuration reference, testing and operating guide: `docs/md/API Gateway/API Gateway — Rate Limiting (Implementation Notes).md`. Threat rationale, why-this-approach and the enforcement plan: `docs/md/CyberSecurity/API Gateway Rate Limiting — Rollout Status.md`. Not duplicated here.

## Gotchas / Notes
- Helmet's defaults set `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Resource-Policy: same-origin`, which can interact with popup-based OAuth flows (Google/LinkedIn login, Wise/Payoneer account-connect) and with the frontend living on a different origin (Vercel) than this gateway. Not yet smoke-tested against a live OAuth popup flow — do that before fully trusting this in production. If COOP ever needs loosening for a specific flow, scope it narrowly (e.g. `crossOriginOpenerPolicy: { policy: 'same-origin-allow-popups' }`) rather than disabling it globally.
- Only api-gateway, `portfolio-service`, and `time-tracking-service` have Helmet as of this entry. The other ~25 services do not — a deliberate, scoped decision (see rollout-status doc), not an oversight. It does mean those services have no browser-facing header hardening if the api-gateway ingress boundary is ever bypassed, as happened in the 2026-08-04 P0 database-exposure incident.
- While scoping a wider rollout, found that `offer-service`'s compiled build output lands at `dist/apps/offer-service/apps/offer-service/src/main.js` (a duplicated path segment), which does not match what its own `start:prod` script expects (`dist/apps/offer-service/src/main`). Likely caused by TypeScript's implicit `rootDir` widening because `offer-service` imports from `@libs/auth`, a path outside its own `src/`. Unconfirmed whether this means `offer-service` currently fails to start in production via `start:prod`. Flagged, not yet investigated further.
- The `@shared/*` path alias (root `tsconfig.json`, mapped to `./shared/*`) is inherited by every service's `tsconfig.app.json`, but nothing in the codebase currently imports from it — unused scaffolding. Don't treat it as a safe, tested vehicle for cross-service shared code without first confirming it resolves at runtime — see the `offer-service` gotcha above, where the one comparable pattern (`@libs/auth`) did not build cleanly.
- **Rate limiting uses a different client IP than `client-ip.controller.ts`.** That controller shows users the leftmost `x-forwarded-for` entry, which is client-controlled. The limiter uses the entry `RATE_LIMIT_TRUSTED_PROXY_HOPS` (default 1) from the right, falling back to the socket. Don't "unify" them: keying limits on the leftmost entry lets anyone reset their bucket by changing a header.
- **`RATE_LIMIT_TRUSTED_PROXY_HOPS` is unverified on Render.** Each process logs once how many `x-forwarded-for` entries it receives (counts only). Confirm it before setting `enforce`: too low reads a proxy address (everyone shares one bucket), too high trusts a client-supplied entry.
- **Middleware order is load-bearing:** `main.ts` is helmet → CORS → per-IP rate limit → body parsers → cookieParser; the module then adds Logging → CsrfOrigin → Jwt → PostAuthRateLimit. CORS must stay above the limiter, or browsers see a CORS error instead of the 429.
- **Do not move the per-IP limiter back into the module.** It sat there until 2026-09-25, when manual testing showed a malformed JSON body is rejected inside `json()` before module middleware runs — so those requests were never counted and could be flooded unseen. Covered by a regression test now.
- Oversized request floods still reach Node before anything can reject them; that is the edge WAF's job, not this limiter's.
- The Render key-value store (free plan, `noeviction`) is shared with BullMQ queues. Rate-limit keys are small and expire, but if memory fills, the queues fail too.
- `favorites-service` imports `@nestjs/throttler`, which is not installed anywhere in `backend/`. Not investigated or changed.

- **Strengthened CSRF / origin trust (2026-09-28).** A missing `Origin` header used to be an unconditional pass on state-changing requests. It is now only a pass when the request cannot be forged: a bearer token is present (desktop app), no auth cookie is present (webhooks, server-to-server), or `Sec-Fetch-Site` says `same-origin`/`same-site`/`none`. Otherwise it is logged, and rejected when `CSRF_STRICT_MODE=enforce` (default `monitor`). Rejecting a write from a non-allow-listed origin is unchanged and always on.
- **localhost is no longer trusted in production.** `FRONTEND_URL` on Render contained `http://localhost:3000`, and `main.ts` also appended it in every environment, so a page on a victim's machine was a trusted origin for both CORS and CSRF against live data. Now stripped in production by both the CORS setup and both copies of the middleware; `ALLOW_LOCALHOST_ORIGIN=true` is the deliberate override. Removed from `render.yaml` too.
- **The Vercel preview CORS pattern is logged, not yet closed.** `vercel.app` is a shared domain, so anyone can deploy an origin matching the pattern and read authenticated responses. Each production match now logs once; set `CORS_ALLOW_VERCEL_PREVIEWS=false` after listing real preview origins in `FRONTEND_URL`. Note this pattern only ever affected CORS — the CSRF check never consulted it.
- **Auth cookies are `SameSite=None` in production** (site on Vercel, API on Render are different sites), so the browser offers no CSRF protection of its own. Full record, including the Phase 3 token design and why a double-submit cookie cannot work cross-site: `docs/md/CyberSecurity/CSRF Defences — Rollout Status.md`.
- The CSRF middleware is duplicated in `auth-service`. Both copies were changed together and must stay in step — there is no working shared-module mechanism between services.
