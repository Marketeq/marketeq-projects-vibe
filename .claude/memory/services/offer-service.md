# offer-service Memory

## Status
Implemented (complete offer lifecycle, counter-offers, milestones, templates, notifications, work schedules — 164 files per progress.md). This file starts at the 2026-10-19 QA retest fix pass; no earlier entries existed.

## Docs Location
Not checked this pass — see /docs/Technical Documentation/ if present.

## What This Service Does
Owns the offer/counter-offer state machine between a client and talent: create/edit/accept/decline/withdraw on both the base `Offer` and `CounterOffer` entities, TTL-based expiry (`ExpiryProcessor`/`ttl.helper.ts`), outbox→Ably realtime publish, and offer-history event logging.

## Entities / Database Tables
- `offer_service.offers` — base offer; `declined_reason`/`declined_chip` (TEXT/VARCHAR(30), nullable) already existed (OS-11).
- `offer_service.counter_offers` — one row per counter in a chain; only the newest is `PENDING`, older ones become `SUPERSEDED` the moment a new counter is created (`CounterOffersService.create()`'s "Step A"). **Does NOT have `declined_reason`/`declined_chip`** — a 2026-10-19 same-day fix added them (migration `1792000000000-AddDeclinedReasonToCounterOffers`), then reverted them the same day once it was established that local offer-service and staging both point at the same cloud DB (72.61.77.231) which cannot be migrated — a schema change here would break every `coRepo.findOne` on that DB. **Do not re-add this migration or these two columns without a real, agreed migration path for that cloud DB.** The decline reason/chip are carried on the `offer.counter_declined` event payload instead (see RabbitMQ Events below) — never persisted on the row.

## API Endpoints
- `POST/PATCH/GET /v1/offers/:offerId/counter-offers[...]` — `counter-offers.controller.ts`. `POST :id/decline` takes a body (`DeclineCounterOfferDto: { reason: string; chip?: DeclineChip }`, kept from the 2026-10-19 pass) — previously took none. The dto is still validated and still flows into `CounterOffersService.decline()`, just no longer written to a column (see above) — only onward into the event payload.

## RabbitMQ Events
- Emits (via outbox): `OFFER_EVENTS.COUNTERED/COUNTER_ACCEPTED/COUNTER_DECLINED/COUNTER_WITHDRAWN/COUNTER_EXPIRED/COUNTER_EDITED` — see `messaging/events/offer-payload-builders.ts`. **`OfferCounterDeclinedPayload` now has optional `declinedReason?: string`/`declinedChip?: DeclineChip` (added 2026-10-19)** — the one event payload in this file that carries a decline reason at all. `OfferDeclinedPayload` (base offer) still does not, and neither withdraw/expire payload does — this is a deliberate, narrow addition for the counter-offer decline DTO this pass added, not a general policy change.
- **No consumer exists anywhere in the backend for `offer.declined` or `offer.counter_declined`** — confirmed via a repo-wide grep across every `backend/apps/*/src`: only `offer-service` itself references either event string. notification-service has no handler for them. This means the new `declinedReason`/`declinedChip` fields on the outbox payload do not currently reach the talent through any notification — they're there for whenever a consumer is built, not a user-visible fix today. See `progress.md`'s 2026-10-19 follow-up entry for the full "where does the reason actually surface" trace (short answer: nowhere, for either the base offer or a counter, in production).

## Key Decisions
- **2026-10-19 (reverted same day)**: `CounterOffer.declinedReason`/`declinedChip` columns + migration — added, then fully reverted (entity, `mapRawToCO`, the `UPDATE` SQL, the migration file) once the shared-cloud-DB constraint was raised. See Entities section above.
- **2026-10-19 (kept)**: `DeclineCounterOfferDto` (controller `@Body()`, service `decline(..., dto?)` param) kept — it's valid, harmless, and now feeds the event payload addition above instead of a column write.
- `OfferConcurrentModificationException` (`offer-state-machine.ts`) no longer puts the raw internal id in its user-facing message — it's thrown with either an offer id or a counter-offer id depending on which CAS update affected 0 rows (both `offers.service.ts` and `counter-offers.service.ts` call sites), so "Offer {id} was modified..." was wrong for every counter-offer call site, and a raw UUID in front of an end user isn't a good message regardless. Message is now generic: "This was just updated elsewhere. Please reload and try again." The `id` constructor param is kept (unused in the message) for any future server-side logging.
